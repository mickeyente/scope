Abstract

Most vibration that matters isn't seismic

Quarries, block industries, construction sites, and busy roads all generate ground vibration that can quietly stress buildings, equipment, and people long before anyone notices — independent of whether a region sees earthquakes at all. Most tools built to measure vibration, seismographs and geophones, are expensive, complex, and built with seismic networks in mind, which puts them out of reach for the local, industrial, and structural contexts where day-to-day monitoring would actually help.

This project builds a cheaper alternative: an SW-420 vibration sensor feeds an ESP32 microcontroller, which judges each reading against a threshold, drives an LED and a 16×2 LCD for instant local feedback, and pushes a timestamped status to Firebase for remote logging. Power comes from an 18650 battery regulated through a TP4056 charger and MT3608 step-up converter, so the whole rig is portable. Across six field tests, it detected simulated and real-world vibration events, responded without noticeable delay, and logged everything to the cloud — evidence that a genuinely affordable, scalable vibration monitor is achievable with parts anyone can source.

The problem

Vibration monitoring exists — just not for places like this

Precise vibration and structural-health instruments are costly to install and maintain, so they cluster around large industrial operations and well-funded infrastructure projects. That leaves smaller construction sites, quarries, block industries, and local communities with no affordable way to track ground disturbance in real time or respond quickly when something looks abnormal.

Even where IoT alternatives exist, sensor sensitivity, unreliable data transmission, and power management in off-grid areas keep holding adoption back. The goal here was a system cheap and simple enough to actually get deployed on sites like these.

Aim

Objectives

  1. Detect ground vibration in real time using the SW-420 sensor.
  2. Classify readings as normal or abnormal against a defined threshold.
  3. Log every event with a timestamp to Firebase for later analysis.
  4. Trigger an immediate visual (LED) alert past the safety limit.
  5. Make vibration trends viewable over time through the cloud dashboard.
System architecture

Four layers, one continuous loop

The system reads, decides, alerts, and logs — every half-to-one second, on repeat.

01 · Sensing

The SW-420 vibration sensor continuously watches for physical ground movement and outputs a signal once vibration crosses a preset trigger, feeding it straight into the ESP32's GPIO pin.

02 · Processing

The ESP32 evaluates whether the signal exceeds a critical threshold. If it does, it fires the buzzer and red LED and prepares the "Alert" status; otherwise it keeps the green LED on and marks the reading "Normal."

03 · Communication

Over built-in Wi-Fi, the ESP32 pushes each event — status plus timestamp — to Firebase as structured JSON, in near real time.

04 · Cloud & display

Firebase stores the incoming stream and makes it available to a live dashboard, while the onboard 16×2 LCD gives an immediate local readout without needing a phone or laptop nearby.

Logic

The decision loop, in plain steps

Boot up, read the sensor, decide, act, log, wait, repeat — about once a second.

// core decision, simplified from the ESP32 firmware
if (digitalRead(sensorPin) == HIGH) {
  digitalWrite(redLED, HIGH);
  digitalWrite(buzzer, HIGH);
  lcd.print("Alert: Vibration");
  Firebase.setString(fbData, "/vibration_data/status", "Alert");
  Firebase.setString(fbData, "/vibration_data/time", currentTime);
} else {
  digitalWrite(greenLED, HIGH);
  lcd.print("Normal");
  Firebase.setString(fbData, "/vibration_data/status", "Normal");
}

Research readiness

What I'd do with more rigor

Two gaps are worth naming plainly, because they're exactly where this prototype would need to grow into a research-grade instrument.

No calibrated ground truth

  • The SW-420 outputs a trigger signal, not a measured physical quantity — so the severity table above communicates intuition, not verified mm/s or g-force values.
  • Next step: log the SW-420 alongside a calibrated MEMS accelerometer (ADXL335 / MPU6050) on the same events, and regress one against the other to get real, defensible units.

Theory outpaced analysis

  • Signal theory and FFT are set up in the framework but never actually run against the field data — the results are threshold crossings, not frequency-domain analysis.
  • Next step: run FFT on logged event windows to see whether frequency content, not just amplitude, can distinguish machinery, traffic, and human-induced vibration.

Neither gap is a flaw in the concept — the sensing, alerting, and cloud-logging loop all worked end to end. They're the difference between a working prototype and a validated instrument, and closing them is the natural next phase of this work.

Conclusion

What it adds up to

Hardware, firmware, and cloud came together into one working loop — cheap sensor in, cloud-logged alert out — validated across six real sites rather than just on a bench.

"Even low, barely noticeable vibrations can signal the beginning of something dangerous — structural weakness or nearby excavation. High vibration levels, often dismissed as part of everyday industrial or high-traffic life, can have long-term impacts if left unchecked."

The system shows that meaningful vibration awareness doesn't require expensive, specialized infrastructure — just a sensor, a microcontroller, and a cloud connection, deployed with intent.

Where it could go next

  • Swap the SW-420 for a calibrated MEMS accelerometer (ADXL335 / MPU6050) to get real mm/s and g-force readings.
  • Add machine-learning filtering to cut false alarms and tell vehicle, human, and machinery vibration apart.
  • Local SD-card backup so no data is lost during Wi-Fi outages.
  • Multiple nodes across a site for synchronized, area-wide monitoring.
  • A mobile app for alerts and history, plus solar power for fully off-grid deployment.

Known limitations

  • SW-420 gives binary/analog output only — no standardized mm/s or g-force units.
  • Sensitive to electromagnetic and environmental noise, which can trigger false positives.
  • Coarse frequency resolution makes it hard to tell vibration sources apart.
  • Depends on live internet access to reach Firebase — no offline buffering yet.
  • Single monitoring point per unit; no multi-zone coverage without more nodes.
